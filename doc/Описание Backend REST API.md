# Описание Backend REST API

## Аутентификация

Все методы аутентификации находятся под префиксом `/auth` и доступны без токена.

Используется модель из двух JWT-токенов:

- **Access-токен** — короткоживущий, передаётся в каждом защищённом запросе в заголовке
  `Authorization: Bearer <accessToken>`. Содержит claims: `sub` (имя пользователя), `id`,
  `email`, `role`. Срок жизни задаётся в `app.token.access.expiration` (по умолчанию `2400` минут).
- **Refresh-токен** — долгоживущий, **не возвращается в теле ответа** (поле `refreshToken`
  в теле всегда `null`). Передаётся клиенту через `HttpOnly`-куку и используется только для
  обновления пары токенов. Срок жизни задаётся в `app.token.refresh.expiration`
  (по умолчанию `30` дней).

Кука с refresh-токеном выставляется так:

```
Set-Cookie: refreshToken=<jwt>; Path=/auth/refresh; Max-Age=2592000; HttpOnly; Secure
```

> `Path=/auth/refresh` означает, что браузер отправит эту куку только на эндпоинт обновления.
> Флаг `Secure` требует HTTPS.

Общий формат тела ответа всех успешных методов аутентификации:

```JSON
{
    "accessToken": "eyJhbGciOiJIUzUxMiJ9.eyJzdWIiOiJJdmFuIiwiaWQiOjEsImV4cCI6MTYyMjUwNj...",
    "refreshToken": null
}
```

---

#### POST `/auth/sign-up`

Регистрация пользователя. **Регистрация ограничена и требует валидного кода приглашения**
(ваучер типа `INVITE`). Принимает объект:

```JSON
{
    "username": "Ivan",
    "email": "ivanov@email.com",
    "password": "My$password123",
    "inviteCode": "PH4FPRD0"
}
```

Ограничения валидации:

- **username** — от 5 до 50 символов, не пустой; должен быть уникальным.
- **email** — от 5 до 255 символов, формат `user@example.com`; должен быть уникальным.
- **password** — не более 255 символов.
- **inviteCode** — код приглашения формата `[A-Z0-9]{8}`. При невалидном/отсутствующем/
  исчерпанном коде возвращается `403 Forbidden`.

В случае успеха возвращает пару токенов (см. общий формат выше) и выставляет куку с refresh-токеном.

---

#### POST `/auth/sign-in`

Авторизация по имени пользователя и паролю. Принимает объект:

```JSON
{
    "username": "Ivan",
    "password": "My$password123"
}
```

Ограничения валидации:

- **username** — от 5 до 50 символов, не пустой.
- **password** — не более 255 символов, не пустой.

В случае успеха возвращает пару токенов и выставляет куку с refresh-токеном.
При неверных данных — `401 Unauthorized`.

---

#### POST `/auth/refresh`

Обновление пары токенов. Тело запроса не требуется — refresh-токен читается из куки `refreshToken`
(она автоматически отправляется браузером на этот путь).

Запрос:

```
POST /auth/refresh
Cookie: refreshToken=<jwt>
```

В случае успеха возвращает новый access-токен в теле и новую куку с refresh-токеном.
При недействительном/просроченном refresh-токене — `401 Unauthorized`.

---

#### POST `/auth/sign-out`

Выход из профиля.

> **Не реализовано.** На текущий момент метод возвращает `501 Not Implemented`.

## Авторизация игрока через плагин (Device Authorization Grant)

> **Статус: проектируется, ещё не реализовано.**

### Зачем это нужно

Сторонние администраторы серверов используют API бэкенда через плагины. Им **нельзя доверять
пароль или личный токен игрока** — скомпрометированный/недобросовестный сервер мог бы
авторизоваться за игрока. Поэтому игрок проходит авторизацию **на сайте** (он работает на этом
же бэкенде), а плагин лишь узнаёт результат, не получая секретов игрока.

Схема построена на **OAuth 2.0 Device Authorization Grant ([RFC 8628](https://datatracker.ietf.org/doc/html/rfc8628))**
с одним важным **отступлением ради безопасности**: по завершении плагин получает не личный токен
игрока, а только подтверждение его верифицированной личности (и, опционально, серверный
session-токен). Имена протокольных полей сохранены из RFC (`device_code`, `user_code`,
`verification_uri`, `expires_in`, `interval`, `grant_type`, `error`) для совместимости со
стандартными OAuth-клиентами.

### Роли (маппинг на термины RFC 8628)

| Термин RFC | В нашей системе |
|---|---|
| Device / Client | Плагин на Minecraft-сервере (имеет выданный при регистрации `client_id`) |
| Verification URI | Страница авторизации на сайте Pixplaze |
| End user | Игрок, зашедший на сервер |
| Authorization Server | Бэкенд Pixplaze |

### Поток

```
1. Игрок заходит на сервер.
2. Плагин → POST /auth/device           (запрашивает сессию для UUID игрока)
   Бэкенд → device_code, user_code, verification_uri, expires_in, interval
3. Плагин даёт игроку в чате кликабельную ссылку (verification_uri с вшитым кодом)
   и держит его в «лимбо», начиная опрашивать статус.
4. Игрок открывает ссылку → логинится на сайте (/auth/sign-in) → подтверждает вход,
   видя, на каком сервере и под каким ником авторизуется.
5. Плагин → POST /auth/device/token     (повторяет с интервалом interval)
   - пока ожидание:  400 { "error": "authorization_pending" } | { "error": "slow_down" }
   - игрок отклонил:  400 { "error": "access_denied" }   → плагин кикает
   - истёк срок:      400 { "error": "expired_token" }    → плагин кикает по таймауту
   - успех:           200 { "status": "approved", "player": {...} } → плагин впускает
```

---

### **POST** `/auth/device` — запрос авторизации устройства

Соответствует [RFC 8628 §3.1](https://datatracker.ietf.org/doc/html/rfc8628#section-3.1).
Публичный (не требует токена игрока), но требует аутентификации **клиента** (плагина).

`Content-Type: application/x-www-form-urlencoded`

Параметры:

- **client_id** (обяз.) — идентификатор сервера/плагина, выданный при его регистрации.
- **player_uuid** (обяз.) — UUID зашедшего игрока. Сессия жёстко привязывается к этому UUID.
- **player_name** (обяз.) — игровой ник; показывается игроку на странице подтверждения.

```
POST /auth/device HTTP/1.1
Content-Type: application/x-www-form-urlencoded

client_id=srv_148&player_uuid=069a79f4-44e9-4726-a5be-fca90e38aaf5&player_name=notch
```

Ответ `200 OK`, `Content-Type: application/json` ([RFC 8628 §3.2](https://datatracker.ietf.org/doc/html/rfc8628#section-3.2)):

```JSON
{
    "device_code": "GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",
    "user_code": "WDJB-MJHT",
    "verification_uri": "https://pixplaze.net/device?user_code=WDJB-MJHT",
    "expires_in": 120,
    "interval": 5
}
```

Поля:

- **device_code** — секрет, которым **плагин** опрашивает статус. Игроку не показывается,
  имеет высокую энтропию.
- **verification_uri** — кликабельная ссылка на страницу подтверждения **со встроенным
  `user_code`**. Плагин отправляет её игроку в чат — вводить код вручную не нужно.
- **user_code** — короткий человекочитаемый **идентификатор сессии**. Игрок его не вводит
  (он уже вшит в ссылку); код показывается на экране подтверждения, чтобы игрок мог сверить,
  что подтверждает именно свою сессию (защита от подмены).
- **expires_in** — время жизни сессии в секундах (рекоменд. согласовать с таймаутом кика).
- **interval** — минимальный интервал опроса в секундах (по умолчанию `5`).

> **Отличие от канонического RFC 8628.** В стандарте предполагается устройство без браузера и
> клавиатуры, поэтому есть два URL: `verification_uri` (голый, для ручного набора) и
> `verification_uri_complete` (со вшитым кодом, для QR/NFC), а пользователь обычно **вводит**
> `user_code` руками. У нас канал к игроку — чат с кликабельными ссылками, поэтому ручной ввод
> не нужен: оставляем **один** `verification_uri` со встроенным кодом, а `user_code` используем
> только как идентификатор сессии для экрана подтверждения.

---

### Подтверждение игроком (страница сайта)

[RFC 8628 §3.3](https://datatracker.ietf.org/doc/html/rfc8628#section-3.3). Игрок переходит по
кликабельной ссылке `verification_uri` (код `user_code` уже вшит в неё — вводить ничего не надо),
**аутентифицируется** обычным способом (`POST /auth/sign-in`, см. выше), после чего страница
показывает `user_code` сессии, **какой сервер** и **под каким ником** запрашивает вход, и
предлагает подтвердить или отклонить. Вспомогательные эндпоинты сайта:

- **GET** `/auth/device?user_code=...` — по коду из ссылки вернуть данные сессии для экрана
  подтверждения (`{ "user_code": "...", "client_name": "...", "player_name": "notch" }`).
  Требует аутентифицированного игрока.
- **POST** `/auth/device/confirm` — подтвердить (`{ "user_code": "...", "approved": true|false }`).
  Требует аутентифицированного игрока.

> **Защита от фишинга** ([RFC 8628 §5.4](https://datatracker.ietf.org/doc/html/rfc8628#section-5.4)):
> на экране подтверждения **обязательно** показывать сервер и ник, под которым идёт вход, и
> требовать явного согласия игрока. Это не даёт недобросовестному админу подсунуть чужую сессию.

### **POST** `/auth/device/token` — опрос статуса (получение результата)

Соответствует [RFC 8628 §3.4–3.5](https://datatracker.ietf.org/doc/html/rfc8628#section-3.4).
Плагин повторяет этот запрос с интервалом `interval`, пока не получит финальный статус или
не истечёт его собственный таймаут.

`Content-Type: application/x-www-form-urlencoded`

```
POST /auth/device/token HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:device_code
&device_code=GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS
&client_id=srv_148
```

**Промежуточные ответы** (`400 Bad Request`, поле `error` по RFC 8628 §3.5):

| `error` | Значение | Действие плагина |
|---|---|---|
| `authorization_pending` | Игрок ещё не подтвердил | Продолжать опрос |
| `slow_down` | Слишком частый опрос | Увеличить интервал на 5 с и продолжать |
| `access_denied` | Игрок отклонил вход | Прекратить опрос, кикнуть |
| `expired_token` | Сессия истекла | Прекратить опрос, кикнуть |

```JSON
{ "error": "authorization_pending" }
```

**Успешный ответ** `200 OK` — **отступление от RFC §3.5**: вместо личного токена игрока
возвращается подтверждение его личности (и опционально серверный session-токен, **не** являющийся
личным JWT игрока):

```JSON
{
    "status": "approved",
    "player": {
        "uuid": "069a79f4-44e9-4726-a5be-fca90e38aaf5",
        "username": "notch"
    },
    "sessionToken": "eyJhbGciOiJIUzUxMiJ9..."
}
```

- **player** — верифицированная личность игрока, **привязанная к тому же `player_uuid`**, что
  был указан в `/auth/device`. Если они не совпадают — это попытка подмены.
- **sessionToken** *(опционально)* — токен, ограниченный областью «этот игрок верифицирован на
  этом сервере». Не даёт доступа к личному кабинету игрока.

## Профиль и серверы

> Разделы ниже описывают ранее запланированный дизайн и **ещё не приведены в соответствие
> с реализацией**. Будут переписаны отдельно.

#### GET `/profile/{user_id}`

Возвращает информацию о профиле игрока в виде объекта:
```JSON
{
    "username": "notch",
    "avatar_url": "https://link.to/avatar.png",
    "visuals": 
    {
        "skin_url": "https://link.to/skin.jpg",
        "cape_url": "https://link.to/cape.jpg"
    },
    "favourite_server_id???": 232,
    "plays_on_server_id???": 232
}
```

#### GET `/profile/{user_id}/stats???`

*Примечание*: требует наличия JWT-токена в заголовке.

Возвращает информацию об общей статистике игрока на всех серверах в виде объекта:
```JSON
{
    "broken_blocks": 52139,
    "jumps": 929319,
    // И так далее...
}
```

#### GET `/server/{server_id}`

Возвращает информацию о сервере в виде объекта:
```JSON
{
    "name": "UberCraft",
    "description": "The best Minecraft server!",
    "ip": "178.255.255.255",
    "port": 25565,
    "map_port": 25566,
    "chat_id": 15,
    "max_players": 100,
    "online_players": 99
}
```

#### GET `/server/{server_id}/players`

Возвращает информацию об онлайн игроках на сервере в виде объекта:
```JSON
{
    "players": [
        {
            "player_id": 0,
            "nickname": "notch"
        },
        {
            "player_id": 1,
            "nickname": "emberati"
        }
    ]
}
```
